# Storyboard 资源流式驻留方案

## 当前原型与上限

Editor/Internal 的本地 v2 谱包已接入图片流式驻留。每脚本最多 **1,024 个 PNG 声明**，每图最多 **4096×4096、16 MiB 文件字节**；声明总量不要求能同时驻留。两档的**在途、就绪和待退役纹理合计**都最多 128 槽，渐变页也占一槽。未改变 Public／商店／录制发布边界。正式视频的后台解码和统一预算未实现，静音 Theora 验证 pilot 仍单独受限。

| 档位 | 物理纹理槽位 | Storyboard 内存口径 |
| --- | ---: | --- |
| 低（移动平台默认） | 128 | **128 MiB 逻辑封套**，解码、上传和待退役按实际任务预留；不能把整档用作就绪贴图预算。 |
| 标准（桌面默认） | 128 | **256 MiB 逻辑封套**，同一预留规则。两档可在“画面与动效”切换，下局生效。 |

512 MiB、1 GiB 和 256 槽只保留为下方离线压力对照，不属于拟提供给玩家的档位。

[预算账本](<../client/scripts/game/gameplay/StoryboardResidencyLedger.cs>)跨局追踪**就绪纹理、在途预留、上传暂存与仍待退役的纹理**。图片按无 mip 的 RGBA8、每行向上对齐 256 B 估算；同路径及同裁口别名共享一份底层纹理。裁口目前仍物理复制以保持线性采样边缘，独立计入；不做跨路径内容去重，原 eager 小图集试验不进入流式版。封套是有界资源申请口径，不等于驱动实时 VRAM 或全进程 RSS；编码容器、引擎/系统共用缓存和独立视频 pilot 不能从封套反推。换档不会超前把未退役的旧资源记成已释放；新局按目标档等可用额度。

## 加载、使用、回收

1. **元数据编译，不预解码全集。** [时域表](<../shared/Storyboard/StoryboardSampler.cs>)把 Bar、祖先活动区间、绝对 clip/repeat 和定毫秒序列折成半开媒体区间，合并重叠和相邻记录；不以动态透明度或画外位置收窄。极密序列超出表的细分预算时，用该段全帧素材的保守集合。`STORYBOARD_WORKING_SET` 报告最密时点与素材需求；编辑器接入这些诊断仍待做。
2. **按截止时点预取。** 首屏音频启动前可预热最多 750 ms（外围谱包／脚本预检另计）；播放中不等待资源。通常 1 秒，近期 I/O＋解码／上传偏慢或两秒内待加载资产密集时扩到 2 秒；OS 内存压力收窄到 0.25 秒、取消推测请求并退役未固定缓存。全局一条后台 I/O／PNG 解码通道，先占槽和字节，再做工作；主线程每帧最多提交一张纹理。超过 **16 MiB 对齐字节**的单图仅在首屏预热时提交；后段若仍未就绪，作者需预切片或提供较小图，否则该段静态降级。不是任意 4K 图实时上传保证。
3. **固定当前，按未来使用回收。** 区间边界更新就绪优先级；挤压时先退役无后续用途，再取下次使用最远、同距时更大的图。[画布](<../presentation/game/storyboard/StoryboardCanvas.cs>)先移除指向 RID 的绘制命令；[RD 账本](<../client/scripts/game/gameplay/StoryboardResidencyLedger.cs>)收到后台队列的 GPU 完成回调后才归还额度，不数固定帧。Windows Vulkan 已验；无 RD 的 OpenGL 兼容渲染回落原背景，headless 只用于行为验证。当前集不完整时整层演出停在静态底，不改绘制顺序；损坏 PNG 在后台发现时恢复原背景。`_Draw` 不读文件或创建图片。
4. **显式跳转建新代际。** 旧请求取消，已就绪且目标还需要的图可重用，退役中的额度仍计。暂停不向前排队（已开始的单个解码可完成），回到同一媒体时间继续；音频越界隐藏而非永久销毁，真正结算／离场取消并释放。切档、跳转与静态降级都不进入 Gameplay Digest、音频时钟、判定或成绩。

## Twin Bloom 全曲审计

原始赛事资源只留在 Git 忽略目录。工具按资源路径合并精确毫秒区间，用 Sprite 作者时间包络和动画帧窗口，不按实时透明度/屏幕剔除收窄；是保守的**图片工作集**，不模拟视频、运行时裁口复制、atlas、后台暂存或系统内存。全曲 **492 路径、783.44 MiB RGBA8**，其中最大单图 **27.98 MiB**，原始 PNG/JPEG 文件合计约 **35.06 MiB**（不是转 PNG 后的下载体积）。

| 时间窗 | 最大资源数 | 最大 RGBA8 字节折算 | 字节峰值时刻 |
| --- | ---: | ---: | ---: |
| 仅当前 | 70 | 117.94 MiB | 297.833 s |
| 当前 + 0.5 s | 86 | 117.94 MiB | 297.333 s |
| 当前 + 2 s | 91 | 120.09 MiB | 295.833 s |
| 当前 + 4 s | 91 | 127.76 MiB | 312.931 s |
| 当前 + 8 s | 93 | 181.36 MiB | 310.204 s |

资源数和字节峰值不是同一时刻。297.833 s 只有 **14 张**当前图却是字节峰值；约 89.9 s 若冷跳，当前 **65 张／27.93 MiB**，连未来 2 秒为 **91 张／71.57 MiB**。跳转虽然能重算依赖，并不意味着纹理能凭空就绪。

另用一个串行加载通道（假设 **80 MiB/s + 1 ms/项**、7 ms 探测网格、首个时点所需资源预热）模拟保留/预取/回收。不含真实引擎 I/O、显卡上传和释放、内存压力、后台争用。下表用 2 秒候选窗；“缺图”是样本网格上有至少一张需要图未就绪的累计时长。

| 有效像素预算 / 槽位 | 占用峰值 | 回收后重载 | 模拟缺图 |
| --- | ---: | ---: | ---: |
| 96 MiB / 128 | 96.0 MiB | 26 | 1.106 s |
| 112 MiB / 128 | 112.0 MiB | 12 | 0.182 s |
| 128 MiB / 128 | 128.0 MiB | 4 | 0 |
| 256 MiB / 128 | 135.4 MiB | 0 | 0 |
| 512 MiB / 128 | 135.4 MiB | 0 | 0 |
| 512 MiB / 256 | 305.6 MiB | 0 | 0 |
| 1 GiB / 256 | 305.6 MiB | 0 | 0 |

同样 80 MiB/s、128 MiB 有效纹理档，缩短预取到 0.5 秒会在约 64.58 秒首次来不及，累计 1.715 秒；把内存升到 1 GiB 且仍然只看半秒也不改善。这解释了为什么**预取深度/截止时限和内存上限要分开调**。高档保留更长历史可以帮助回跳，但这个顺播样本没有测出 512 MiB／1 GiB 优势。缺图数字是模型，不是玩家目测时长，更不是设备验收。

**低档候选**：只把长边超过 2048 px 的 15 张图按比例缩小，估算当前峰值 **79.91 MiB**、2 秒候选窗 **95.84 MiB**。以 96 MiB 有效预算／128 槽、2 秒窗，40 与 80 MiB/s 两种假设均无缺图采样；改为长边 1536 则影响 41 张，2 秒窗约 88.60 MiB。这里只重新估算尺寸，未生成低档图或验收观感，先试 2048。补测本机逐张 Pillow 读入并展开 RGBA：P50 **1.16 ms**、P95 **17.50 ms**、最慢 **62.38 ms**；不含 Godot/GPU 或移动设备，足以说明不能把这种同步工作插进普通游玩帧。

## 验证入口和剩余工作

- [独立原生回归场景](<../client/scenes/verification/storyboard_residency.tscn>)使用[原创五谱夹具](<../tools/storyboard-demo/generate_streaming_fixture.py>)。在隔离 Godot 进程中设绝对 `DUV_VERIFY_PACK` 与 `DUV_STORYBOARD_MEMORY_MIB=128` 或 `256` 后启动该场景。配合核心测试验证 1024/1025 声明、129 张同屏静态降级、裁口别名、seek、GPU 退役与 8 张 16 MiB 大图压测；见[实际记录](<verification.md#2026-11-28--storyboard-审查修复与流式驻留>)。
- Editor/Internal 性能入口可用 `DUV_STORYBOARD_PREFETCH=1` 或 `2` 固定候选窗。`STORYBOARD_RESIDENCY` 含解码／提交 P95/P99、封套/槽位峰值、重载、资源不足帧和待退役峰值；`STORYBOARD_READY` 另记从挂载到首次可画有内容、上次跳转到目标可画。第一指标包含作者延迟开场，不等于首图 I/O 延迟。两档的完整顺播、多次冷跳、长时间 RSS／graphics counters、动态系统内存回收及真实谱面像素仍待专测。
- 接下来优先验证预切片或后台压缩上传、低档素材变体与正式视频统一预算，再在低端及高端 iPad/Android 热稳后量实呈现、P95/P99 和系统回收／OOM。低档目标 60 Hz、高端按实际 120/144 Hz；当前 Windows 记录不能证明目标真机达标。

运行：`python -B tools/storyboard-demo/residency_audit.py --decode`；纯数据回归：`python -B -m unittest discover -s tools/storyboard-demo -p 'test_residency_audit.py'`。两者只读本地素材，脚本输出 JSON，不生成或公开素材。
