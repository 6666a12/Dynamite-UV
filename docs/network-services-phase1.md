# 网络服务第一阶段设计

> 2026-11-12，设计讨论记录，尚未实现。本页集中维护已确认范围、建议方案与待定事项；不是冻结的 API/数据库合同，也不是部署或发布授权。当前实现见 [handoff](handoff.md)，实际检查见 [verification](verification.md)。

## 1. 已确认的产品范围

以下来自用户在本轮讨论中的明确决定：

- 游戏永久免费，谱面下载免费；不做支付、订单、虚拟货币或购买权益。
- 第一阶段只做账号、免费谱面下载游玩和成绩上传；**段位与联机均不做**。此前将基础段位纳入第一阶段的设想已被本决定取代。
- 谱面暂时只由管理员上架；公众投稿、上传审核网站和专门的创作者模块留待后续。
- 开放注册，暂不做邮箱、短信、验证码等注册验证；具体账号字段与恢复方式尚未确定。
- 服务器成绩先提供本人记录，不做排行榜。
- 游玩结算时：有登录账号则尝试上传一次；未登录则提示未上传。上传失败提供手动重试。
- 上传状态主要用图标表达，不在结算页堆叠说明文字。
- 未登录时，谱面商店、段位、联机入口维持灰色；第一阶段即使已登录，段位和联机也不开放。
- 需要设计谱面商店页、登录页；首页区分登录状态，登录页提供切换服务器的方法。
- 服务器应允许其他有意愿的管理者在满足部署条件时自行部署，不绑定唯一官方实例。
- 不必继续沿用外层 C++ 服务骨架；后续可能为服务器管理者引入脚本扩展，但不属于第一阶段。
- 本轮先记录文档；用户将另行要求接入 Penpot。目前不连接 Penpot、不配置凭据、不修改设计稿。

## 2. 当前工程基础与接入边界

- 首页在线入口仍是占位，没有账号、商店或段位页面；网络服务尚未接入客户端。
- 外层 `server/main.cpp` 仅为 C++ HTTP/Asio 初始化骨架，不构成成熟业务后端或不可更换的技术选型。
- strict v2 已有稳定 `packId`、包内 `chartId`、revision 和 Gameplay Digest；[v2 合同](chart-format-v2.md)不定义服务器协议，不因本轮讨论修改冻结格式。
- 客户端已有本地目录谱包扫描、严格加载、单曲游玩和本地最佳成绩。扫描器不是下载/安装器，现有缓存也不自动处理同 ID 在线更新。
- 现有本地成绩身份为包/差分/规则/Digest，未包含服务器账号身份，Standard/Hardcore 模式隔离也未完整建立；不能直接当作账号云存档。
- `ShowResults` 是单曲结算接入点。在线上传应独立于“是否刷新本地 BEST”，不以整个 `scores.json` 作为上传请求。
- 带时间戳的输入缓冲不是持久回放系统；服务器收到结果不代表已经防作弊认证。

## 3. 服务器身份与账号隔离（建议方案）

建议第一版采用“一次连接一个服务器，每个服务器独立账号、曲库和成绩”，不做联合登录或跨服数据互通。具体服务器身份协议仍待定义。

- 相同用户名在不同服务器不代表同一个账号。
- 切换服务器不能携带上一台的密码、访问令牌或刷新令牌；请求重定向也不得将凭据泄露到其他来源。
- 首版可保存服务器地址列表，切换后重新登录；是否保存多套会话待定。会话秘密应使用适当的系统安全存储，不写入普通配置或日志。
- 登录页同时展示服务器名称和实际地址；远程连接使用 HTTPS，开发用本机例外应显式限定。
- 添加服务器先进行无凭据的协议/兼容性检查，再允许发送登录信息。服务器名称是展示信息，不是可信身份凭证。
- 账号资料交给所选服务器运营者管理，应让用户知情；不暗示所有实例均由项目方运营。
- 断网与注销不同：连接异常不应自动抹掉账号状态，也不影响本地普通游玩。

开放注册不等于关闭基础安全：仍需安全密码哈希、权限检查、注册/登录限流、请求大小和字段限制。暂不增加用户侧验证步骤。若不收验证邮箱，可考虑管理员重置，但账号恢复流程尚未拍板。

## 4. 免费曲库与安装（建议方案）

首版建议提供列表/搜索、谱包详情、下载、更新和本地删除；管理员通过受控工具或管理接口上架/下架，不先建设公共网站。

### 内容身份

明确区分：

- `packId + chartId`：谱包与差分身份。
- 发布版本：这次分发的具体内容；服务端发布模型与 v2 revision 的对应关系待定。
- Gameplay Digest：玩法内容身份，不覆盖全部展示元数据。
- 文件 SHA-256：下载文件完整性，不是成绩真实性证明。
- 安装来源：来自哪个服务器，或由用户手工导入。

不同服务器可以使用相同包 ID，不能互相覆盖；建议在客户端安装登记中维护来源与版本，不向冻结的谱面格式强塞账号信息。服务端发布命名空间及包 ID 冲突策略还需细化。

### 安装生命周期

建议流程：获取版本清单 → 临时下载 → 校验大小/哈希/严格谱包结构 → 安全安装 → 更新谱库与缓存。失败或取消不破坏已有可玩版本，未完成内容不进入选曲列表；更新不能替换当前游玩正在读取的内容。

需要新增下载管理和缓存失效边界，而不是仅覆盖文件后调用重新扫描。下载任务建议不依附页面生命周期；是否跨应用退出续传不属于已确认需求。

服务器及下载内容按不可信输入处理：限制压缩/解压体积、文件数量和路径，拒绝目录逃逸及危险链接，不执行包内代码。自建实例不自动具有客户端代码执行权。

管理员上架仍需记录作者、音频/曲绘/谱面授权、发布版本和下架原因。免费不等于可以分发未经授权素材；`client/testdata/` 不得作为公共库存。具体要求见 [发布说明](releasing.md)。

## 5. 成绩上传与本人记录

### 已确认行为

- 结算时尝试一次；未登录提示未上传；失败提供手动重试。
- 主要用图标呈现上传状态。
- 服务器记录只面向本人，不做排行榜；反作弊留待后续。

### 建议的实现边界

- 本地成绩先独立保存；网络上传异步进行，不阻塞结果页，不因网络失败丢弃本地成绩。
- 每次游玩创建唯一 `playId` 和不可变结果快照。重试使用同一个 ID；服务端在相应账号范围内幂等保存，处理“已保存但响应丢失”的情况。
- 上传本次游玩，而不是仅上传刷新 BEST 的结果。本人历史记录和服务器端最佳成绩摘要的存储、查询范围待定。
- 请求带谱面内容身份、规则版本、模式/修饰项和判定统计；服务端核对接受的谱面版本。不能仅按包名或分数识别成绩。
- Auto、调试/验证游玩应与正常成绩区分；正式上传条件、失败局是否保存、手工导入谱面的接受规则待定。
- 已绑定服务器/账号的游玩不得在重试时改投另一身份；具体绑定时点及未登录开局如何补登录上传见待定事项。
- 第一版建议不做后台自动补传队列；离开结果页后不承诺可补传。此限制尚待交互设计确认。
- 保存结果应标识为客户端上报、未经反作弊认证，后续不能无条件转换为可信竞技记录。基础鉴权、范围校验、去重和限流不属于可省略的反作弊专项。

### 图标状态建议（具体造型未定）

| 状态 | 图标语义 | 建议交互 |
| --- | --- | --- |
| 上传中 | 云上传＋旋转指示 | 防止重复点击 |
| 上传成功 | 云＋对勾 | 按需显示服务器和状态 |
| 上传失败 | 云＋重试/感叹号 | 点击重试原结果 |
| 未登录/会话过期 | 云＋锁 | 点击进入登录 |
| 本次不可上传 | 云＋斜线 | 按需解释原因 |

默认不显示长文字，但不能只靠颜色区分。桌面悬停提示、触屏反馈和可访问名称需一起设计；未登录应表达为“未上传”，而不是假装发生了网络请求失败。

## 6. 页面设计与后续 Penpot 工作

本节是设计清单，不是已经完成的设计稿或实现验收。

### 登录/注册与服务器切换

- 展示服务器名称、地址、连接状态和兼容性。
- 添加/选择服务器；切换时清晰说明账号归属变化。
- 登录、开放注册表单；用户名冲突、密码错误、网络失败、会话过期等状态。
- 账号字段、密码规则、恢复方式和登录保持策略待定。
- 是否作为独立场景或覆盖式页面、从结算进入后能否无损返回，留待设计确认。

### 谱面商店

- 当前服务器、搜索/列表、空状态、加载/连接错误。
- 谱包详情：封面、曲名、作者、差分、版本、大小和授权展示。
- 未安装、下载中、已安装、可更新、下载失败状态及对应操作。
- 详情用侧栏/弹层还是独立页面待定；不强制新增第三个主页面。

### 首页与结算的配套状态

- 首页：未选择服务器、未登录、已登录昵称/服务器、登录过期、连接异常。
- 商店登录门禁；段位/联机持续禁用，CREDITS 不因本任务开放。
- 结算：上传状态图标、失败重试及未登录入口，与现有结果布局协调。
- 本人记录查看入口及历史列表范围尚待定义，不能把“上传成功图标”当成记录查看功能已完成。

### Penpot 接入边界

用户将稍后另行要求在 Claude Code 中接入 Penpot。本轮不实施 MCP 配置或设计稿修改。接入前阅读 [设计位置与 MCP 安全规则](editor-ui-design.md)，核实当前工具与目标文件/页面；历史 DSH/Codex 配置不能证明当前会话已配置。

**token 是密钥，不进仓库，不打印含 token 的完整 URL。** 本文不保存连接凭据。设计材料不等于实机实现或验收；后续改稿应限定到确认的游戏页面，保留其他设计内容。

## 7. 后端与自部署交付（建议，未冻结选型）

推荐 ASP.NET Core 模块化单体，数据库用 PostgreSQL；账号、曲库发布、成绩、管理分别拥有业务状态，不把 HTTP 请求写进游戏判定或每帧逻辑。不因未来联机预先引入微服务。

建议首版支持本地磁盘保存谱包和封面，对象存储作为可选后端；不强制第三方部署者购买指定云服务或邮件服务。具体框架版本、持久化库、对象存储协议和部署平台尚未选定。

自部署交付应考虑：

- 配置样例、数据库迁移、容器化启动说明和最低环境要求。
- 初始管理员创建、上架/下架工具、权限和管理审计。
- HTTPS/反向代理、上传与注册限流、磁盘配额、基础运行日志。
- 数据库与谱包的备份、恢复，以及升级失败的处理。
- 客户端/服务器协议版本与最低兼容要求；不兼容时清楚拒绝而非带错请求继续执行。
- 项目目前无项目级 LICENSE。允许第三方部署/分发的正式授权条款尚需确定；免费产品政策不自动授予源代码或素材再分发权。

## 8. 后续路线，不纳入第一阶段

- 段位：用户曾提出连续三曲、独立血量，血量不掉空即可继续，最终评级/镀层由分数及其他因素决定。**本轮已延后整个段位功能**；每曲是否重置血量、具体数值、失败规则和评级公式均不在此冻结，不能把助手此前解释自动当作用户批准。
- 多路线、自定义 debuff，以及供管理员使用的脚本语言属于后续想法。可先考虑声明式配置和已知 modifier；语言、沙箱、执行位置与确定性方案都未选定。不授权客户端执行任意服务器下发代码。
- 实时联机、排行榜、反作弊/回放验证、公众投稿审核网站均留后续；没有排期或实施授权。
- 不做支付、订单、虚拟货币，保持游戏永久免费。

## 9. 实施前仍需细化

1. 账号标识字段、密码规则、退出/保持登录、无验证条件下的账号恢复流程。

4. 可上传的游玩模式、失败/中断局处理、规则版本以及服务端数据保留策略。
